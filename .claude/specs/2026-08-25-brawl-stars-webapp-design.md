# 브롤스타즈 컴패니언 웹앱 설계 문서

작성일: 2026-08-25
관련 문서: [브롤스타즈 API 레퍼런스](../docs/brawl-stars-api-reference.md)

---

## 1. 개요

### 1-1. 무엇을 만드나

브롤스타즈 플레이어가 자기 계정을 조회하고, 브롤러 정보를 찾아보고, 자기 성향에 맞는 브롤러를 추천받는 공개 웹앱. PWA로 만들어 설치 가능한 형태까지 간다.

화면은 홈과 다섯 개 탭으로 구성한다.
```
  홈        요약 대시보드 — 유저 순위 · 클랜 순위 · 진행 중 이벤트 · 내 계정
  브롤러    전체 도감과 상세
  랭킹      플레이어 · 클럽 랭킹
  이벤트    현재 로테이션
  추천      성향 기반 브롤러 추천
  프로필    내 계정 상세 (상단바 아바타로 진입)
```

### 1-2. 타겟과 언어

주 타겟은 **해외 사용자**, 기본 언어는 **영어**. 한국어를 동등하게 지원한다.

- 기본 로케일: `en`
- 지원 로케일: `en`, `ko`
- 첫 방문 시 `Accept-Language`로 판별하되, 사용자가 바꾸면 그 선택을 우선한다

### 1-3. 확정된 전제

- 공개 서비스 (누구나 태그를 넣고 조회)
- 로그인 없음 — 개인 설정은 브라우저 로컬에 저장
- DB 사용 — 배틀로그가 25건만 내려오는 한계를 넘어 전적을 축적하기 위함
- 추천은 설문과 계정 데이터를 함께 쓰는 하이브리드
- AI는 개발자 무료 키로 돌리되 한도 초과 시 사용자 키(BYOK)로 넘긴다

### 1-4. 성공 기준

- 태그만 입력하면 30초 안에 자기 전적과 추천 결과를 볼 수 있다
- 태그가 없어도 홈·브롤러·랭킹·이벤트와 설문 기반 추천이 완전히 동작한다
- 영어·한국어 어느 쪽으로 들어와도 브롤러 이름·역할·게임모드가 모국어로 보인다
- 개발자에게 청구되는 금액이 0원이다

## 2. 기능

### 2-1. 공통 — 다국어

**게임 데이터 이름**은 UI 번역 파일이 아니라 빌드타임에 생성한 게임 데이터에 `{ en, ko }` 형태로 내장한다. 브롤러 이름, 역할, 설명, 게임모드 이름이 여기 해당한다.

**UI 문구**는 별도 메시지 파일(`messages/en.json`, `messages/ko.json`)로 관리한다.

한글 데이터 확보 경로는 실측으로 검증했다.

**브롤러 한글명·설명·역할**
  - 경로: BrawlAPI `/game/csv_logic/characters`의 내부 코드명 → `TID_{SCREAMING_SNAKE}` → `/game/localization/kr`
  - 예: `ShotgunGirl` → `TID_SHOTGUN_GIRL` = "쉘리", `_DESC` = 긴 설명, `_SHORT_DESC` = "대미지 딜러"
  - 실측 커버리지: 이름·설명 102/106, 역할 83/106

**게임모드 한글명**
  - 경로: 공식 API `/events/rotation`의 `event.modeId` → `TID_GAME_MODE_{modeId}` → 한글명, `_DESC` = 설명
  - 예: `TID_GAME_MODE_0` = "젬 그랩"

**검색**은 현재 UI 언어와 무관하게 영문명과 한글명을 모두 인덱싱한다. 영어 UI에서 "쉘리"를 쳐도, 한국어 UI에서 "shelly"를 쳐도 잡혀야 한다.

### 2-2. 홈

앱의 첫 화면. 정보를 카드 섹션으로 나눠 한눈에 훑을 수 있게 한다. 섹션마다 헤더와 "전체 보기" 링크를 두고, 링크는 해당 탭으로 이동한다.

**섹션 1 — 유저 순위**
  - 글로벌 플레이어 랭킹 상위 5명
  - 순위, 프로필 아이콘, 이름, 트로피, 클럽명. 1·2·3위는 랭킹 탭과 동일한 금·은·동 배지
  - 대표 계정이 이 안에 있으면 [내 계정] 라벨

**섹션 2 — 클랜 순위**
  - 글로벌 클럽 랭킹 상위 5개
  - 순위, 클럽 뱃지, 이름, 트로피, 멤버 수

**섹션 3 — 진행 중인 이벤트**
  - 로테이션에서 **5개**만 노출. 정렬은 **종료 임박순**이라 "지금 뭘 해야 하나"에 바로 답한다
  - 게임모드 아이콘, 모드명(현지화), 맵 이름, 남은 시간

**섹션 4 — 내 계정** (대표 계정이 설정된 경우에만)
  - 프로필 아이콘과 이름
  - **대표 브롤러** — 브롤스타즈 API에 "대표 브롤러" 개념이 없으므로, 보유 브롤러 중 **트로피가 가장 높은 브롤러**를 대표로 계산해 보여준다. 이미지, 이름, 트로피, 랭크, 파워
  - 계정 정보 — 트로피, 최고 트로피, 경험치 레벨, 3v3·솔로·듀오 승수
  - 대표 계정이 없으면 이 섹션 자리에 [내 계정 설정하기] 안내 카드를 둔다

**데이터 로딩** — 홈은 서버 라우트 `/api/home` 하나로 묶어 내려준다. 클라이언트가 랭킹·클럽·이벤트·플레이어를 각각 요청하면 왕복이 네 번이 되고, 브롤스타즈 API 호출도 그만큼 늘어난다.

서버에서 짧게 캐시한다.
```
  플레이어·클럽 랭킹   10분
  이벤트 로테이션      30분
  내 계정              캐시하지 않음 (조회 시 스냅샷도 함께 저장)
```

한 조각이 실패해도 나머지 섹션은 보여준다. 실패한 섹션 자리에만 재시도 버튼을 둔다.

### 2-3. 내 프로필

- 태그 입력 → 조회. 입력 시 유효 문자(`0289PYLQGRJCUV`)를 클라이언트에서 먼저 검증해 잘못된 태그로 API를 때리지 않는다
- 조회 결과 상단에 **[내 계정으로 지정]** 버튼. 누르면 확인 모달이 뜬다
  - 문구: "해당 계정을 대표 계정으로 설정할까요?" / 버튼: [취소] [확인]
  - 확인하면 로컬스토리지에 저장되고 상단바에 프로필 아이콘이 뜬다
  - 이미 대표 계정인 계정을 보고 있으면 버튼 대신 **[대표 계정]** 배지를 보여주고, 옆에 해제 버튼을 둔다
  - 다른 계정을 보다가 지정하면 기존 대표 계정을 덮어쓴다. 모달 문구에 이 사실을 덧붙인다
- 대표 계정 외에 **즐겨찾기 태그**를 여러 개 저장 가능 (친구·클럽원 조회용)
- 표시 항목: 트로피, 최고 트로피, 경험치 레벨, 3v3·솔로·듀오 승수, 소속 클럽
- **트로피 추이 그래프** — DB에 쌓인 일별 스냅샷 기반. 데이터가 하루치뿐이면 그래프 대신 안내 문구
- **보유 브롤러 그리드** — 파워/랭크/트로피 표시, 정렬·필터 가능
- **최근 전투 목록** — 모드, 맵, 결과, 트로피 변동, 사용 브롤러

### 2-4. 브롤러

- 전체 브롤러 그리드. 이미지는 `cdn.brawlify.com` URL을 직접 사용
- **무한 스크롤, 30개 단위.** 단 브롤러 데이터는 빌드타임 정적 번들이라 **서버 호출이 아니라 클라이언트 점진 렌더링**이다. 106종 전체가 이미 메모리에 있고, 30개씩 DOM에 붙인다
  - 실익은 이미지다. 106장을 한꺼번에 요청하지 않아 첫 화면이 빨라진다
  - 구현 시 랭킹 탭과 같은 무한 스크롤 훅을 쓰되, 데이터 소스만 로컬 배열로 주입한다
- 검색(영문·한글 동시), 필터(역할, 희귀도), 정렬(이름, 희귀도, 출시순). 필터가 바뀌면 스크롤 위치와 렌더 개수를 초기화한다
- 대표 계정이 있으면 각 카드에 **내 진행도(파워/랭크/트로피)를 오버레이**하고, 미보유 브롤러는 흐리게 처리
- 카드 클릭 시 **페이지 이동 없이 상세 패널**이 열린다 (데스크톱은 사이드 드로어, 모바일은 바텀시트)
- 상세 내용: 이미지, 역할, 희귀도, 설명, 수치 스탯(체력·이동속도·사거리), 스타파워·가젯 목록, 사용 가능 기어, 내 진행도, AI 사용법, AI 추천 기어

### 2-5. 랭킹

**플레이어 랭킹과 클럽 랭킹**을 서브 탭으로 제공한다. 홈의 클랜 순위 섹션이 클럽 랭킹을 쓰므로 v1에 함께 넣는다. 커서 페이지네이션 동작은 실측으로 검증했다.

**데이터 소스**
```
  GET /rankings/{countryCode}/players?limit=30[&after={cursor}]
  응답  items[] : tag, name, nameColor, icon.id, trophies, rank, club.name
        paging  : { cursors: { after, before } }
```

- **무한 스크롤, 30개 단위.** 응답의 `paging.cursors.after`를 그대로 다음 요청에 넘긴다. 커서는 불투명 토큰이므로 직접 만들어 쓰면 `400`이 난다
- **총 200위가 상한**이다. 200개를 채우면 `paging.cursors`가 비어서 내려오고, 그게 끝 신호다. 목록 하단에 "상위 200위까지 제공됩니다"를 명시한다
- 국가 선택: 기본은 `global`, 드롭다운으로 국가 전환. 해외 타겟이므로 글로벌을 기본값으로 둔다
- **클럽 랭킹**은 `/rankings/{countryCode}/clubs`로 응답 구조가 거의 같다 (`badgeId`, `memberCount` 추가, `nameColor` 없음). 목록 컴포넌트를 **랭킹 종류를 파라미터로 받는 형태**로 만들어 두 서브 탭이 같은 구현을 공유한다

**표시 규칙**
- **1·2·3위 강조** — 순위 배지에 금·은·동 색상과 별도 스타일. 나머지는 숫자만
- **내 계정 하이라이트** — 대표 계정이 설정돼 있고 그 태그가 목록에 있으면 행 테두리를 강조하고 **[내 계정]** 라벨을 붙인다
- `nameColor`는 `0xffcb5aff` 형태의 ARGB 문자열이다. 앞 2바이트가 알파이므로 CSS로 쓰려면 `#RRGGBB`로 변환해야 한다

**상세 패널** — 브롤러와 동일하게 페이지 이동 없이 패널이 열린다. 다만 브롤러 상세는 정적 데이터인 반면 **플레이어 상세는 `/players/{tag}` 호출이 필요하다.** 같은 태그를 반복해서 열 때 매번 API를 때리지 않도록 클라이언트에서 캐시한다.

### 2-6. 이벤트

현재 로테이션 중인 이벤트 전체를 보여준다.

**데이터 소스** — `GET /events/rotation`. 실측 기준 **15개 슬롯**이 내려온다.

**API 한계를 먼저 명시한다.** 실측해보니 응답에 담기는 건 **진행 중인 슬롯뿐**이고, 예정 이벤트도 종료된 이벤트도 들어 있지 않았다 (진행중 15 / 예정 0 / 종료 0). 즉 **종료된 이벤트를 조회할 방법이 공식 API에 없다.** 히스토리를 만들려면 로테이션 스냅샷을 직접 쌓아야 하는데, v1 범위에서는 하지 않는다.

**표시**
- 15개를 **종료 임박순**으로 정렬. 홈의 이벤트 섹션은 이 목록의 상위 5개와 같다
- 각 항목: 게임모드 아이콘, 모드명(현지화), 맵 이름, 맵 이미지, 남은 시간
- 모드 이름과 설명은 `event.modeId`로 `TID_GAME_MODE_{modeId}`를 조회해 현지화한다
- 모드별 필터

**시각 처리** — `startTime` / `endTime`이 `20260824T080000.000Z` 형태의 변형 ISO라 `new Date()`로 바로 파싱되지 않는다. 전용 파서를 거친 뒤 **사용자 로컬 타임존**으로 변환해 표시한다. 해외 사용자가 주 타겟이므로 UTC 그대로 노출하면 안 된다.

**남은 시간**은 1분 간격으로 갱신한다. 슬롯이 만료되면 목록에서 제거하고, 전부 만료되면 로테이션을 다시 불러온다.

### 2-7. 추천

- 설문 5문항 → 선호 벡터
- 대표 계정이 있으면 계정 데이터에서 실제 벡터를 뽑아 가중 합산
- 결과를 두 그룹으로 나눠 보여준다
  - **이미 잘 쓰는 브롤러** — 성향에 맞고 이미 트로피가 높은 쪽. 검증 역할
  - **안 써봤는데 맞을 브롤러** — 성향에 맞지만 미보유이거나 트로피가 낮은 쪽. 이 기능의 실질적 가치
- 각 결과에 근거 설명을 붙인다. 기본은 사전 생성물 + 템플릿 조합이라 즉시 표시되고 AI 호출이 없다
- 각 결과 하단에 **"AI에게 더 물어보기"** 버튼. 누른 경우에만 실시간 AI가 더 구체적인 답을 쓴다
- 설문 응답은 로컬스토리지에 저장해 다시 방문해도 유지

### 2-8. AI

**기본은 전부 사전 생성이고, 사용자가 명시적으로 요청할 때만 실시간 호출한다.**

**사전 생성 (계정 무관)**
  - 세 종류: 브롤러 사용법, 추천 기어, **브롤러 성향 설명**
  - 106종 × 3종류 × 2언어 = **636건**을 로컬에서 한 번 생성해 **정적 파일로 레포에 커밋**한다
  - 저장 위치: `public/data/ai/{locale}/{brawlerId}.json` (브롤러별 분할, 건당 약 3KB)
  - 사용자 요청 시 AI 호출 0회, DB 조회도 0회. CDN에서 파일 하나를 받는다
  - **생성 결과를 사람이 검토·수정할 수 있다**는 게 DB 대비 가장 큰 이점이다. AI가 틀린 내용을 쓰면 파일을 고쳐 커밋하면 된다

"브롤러 성향 설명"은 추천 근거를 사전 생성물로 만들기 위한 조각이다. "이 브롤러가 **어떤 성향의 사람에게** 맞는지"만 쓰고, 특정 사용자를 언급하지 않는다. 사용자 쪽 문구는 규칙 기반 템플릿이 채운다 (5-5 참조).

**실시간 (옵트인)**
  - 추천 결과의 "AI에게 더 물어보기" 버튼을 누른 경우에만 호출한다
  - 사용자 벡터와 브롤러 정보를 함께 넣어 더 구체적인 답을 생성한다
  - **무료 한도를 소모하는 유일한 지점**이므로 레이트리밋은 여기에만 건다. 버튼을 누르는 사람이 소수라 한도 압박이 크게 줄어든다

공통 규칙:
  - 호출은 서버 라우트에서만. 프롬프트도 서버가 조립한다
  - **사용자 자유 입력은 v1에서 제외** — 프롬프트 인젝션과 한도 폭주를 동시에 막는다
  - AI가 추천 자체를 하지 않는다. 추천은 규칙 기반 스코어링이 하고 AI는 설명만 쓴다. 그래야 존재하지 않는 브롤러를 지어내지 않고, 같은 입력에 같은 답이 나온다
  - AI 실패 시 규칙 기반 결과는 그대로 노출하고 설명 영역만 비활성화한다

- 상단바 우측 프로필 아이콘은 대표 계정의 `icon.id`로 CDN 이미지를 띄운다. 클릭하면 프로필 탭으로 이동
- 대표 계정이 없으면 그 자리에 "Set your account" 버튼

### 3-2. 라우팅

```
  /                    → Accept-Language 판별 후 /{locale}로 리다이렉트
  /{locale}            → 홈
  /{locale}/brawlers   → 브롤러
  /{locale}/ranking    → 랭킹
  /{locale}/events     → 이벤트
  /{locale}/recommend  → 추천
  /{locale}/profile    → 내 프로필
```

홈이 기본 진입점이다. 대표 계정이 없어도 유저 순위·클랜 순위·이벤트 세 섹션이 채워지므로 첫 방문자가 빈 화면을 만나지 않는다.

브롤러 상세는 별도 라우트가 아니라 쿼리 파라미터(`?brawler={id}`)로 패널 상태를 표현한다. 페이지 이동은 없지만 뒤로가기와 링크 공유가 동작한다.

### 3-3. 온보딩

첫 방문자는 홈에 도착한다. **다섯 탭 중 프로필만 태그를 요구하고 나머지는 태그 없이 완전히 동작한다.** 홈은 네 섹션 중 세 개가 채워지고, 내 계정 섹션 자리에 [내 계정 설정하기] 카드가 들어간다.

프로필 탭에 처음 들어가면 태그 입력 화면이 뜬다. **자기 태그를 어디서 보는지 모르는 사용자를 위해 게임 내 위치를 그림과 함께 안내**한다.

랭킹 탭은 대표 계정이 없으면 [내 계정] 하이라이트만 표시되지 않는다.

추천 탭은 태그 없이도 설문만으로 동작하되, 결과 하단에 "대표 계정을 설정하면 실제 플레이 데이터로 정확도가 올라갑니다" 안내를 붙인다.

### 3-4. 상태 처리

**로딩**
  - 브롤러 그리드는 스켈레톤. 정적 데이터라 실제로는 거의 즉시 뜬다
  - 계정 조회는 스피너 + 예상 소요 안내

**빈 상태**
  - 대표 계정 없음 → 홈의 내 계정 섹션에 [내 계정 설정하기] 카드, 프로필 탭에서는 태그 입력 유도
  - 스냅샷 1개뿐 → 그래프 대신 "내일부터 추이가 쌓입니다"
  - 검색 결과 없음 → 필터 초기화 버튼

**에러**
  - `503` 게임 점검 → 전용 화면. 슈퍼셀 업데이트마다 실제로 발생하므로 반드시 만든다
  - `404` 없는 태그 → 태그 형식 재확인 안내
  - `429` 브롤스타즈 API → 백오프 후 DB의 마지막 스냅샷으로 폴백하고 "최신 데이터가 아닙니다" 표시
  - `403` → 사용자에겐 일반 오류. 키·IP 문제는 운영 이슈이므로 서버 로그로만 남긴다
  - AI 한도 초과 → "더 물어보기" 버튼만 비활성화하고 BYOK 입력란을 안내한다. 사전 생성 근거 문구는 그대로 보인다

### 3-5. 반응형 · PWA

- 모바일 우선. 브롤러 그리드는 화면 폭에 따라 2~6열
- `manifest.json` + 서비스 워커로 설치 가능하게
- 오프라인 캐시 범위는 정적 게임 데이터와 앱 셸까지. 계정 데이터는 네트워크 필수로 두고 오프라인이면 명시적으로 안내

### 4-3. 외부 API 사용 규칙

**공식 브롤스타즈 API**
  - 반드시 `https://bsproxy.royaleapi.dev/v1` 경유. Vercel 함수 IP가 유동적이라 직접 호출은 403이 난다
  - 키는 서버 환경변수에만. 클라이언트 번들에 절대 포함하지 않는다

  - 랭킹은 커서 페이지네이션을 그대로 통과시킨다. 서버가 커서를 해석하거나 재생성하지 않는다

**BrawlAPI (비공식)**
  - **런타임에 호출하지 않는다.** 빌드타임에만 받아서 결과를 레포에 커밋한다
  - 비공식 서비스가 죽어도 사이트는 영향을 받지 않는다

### 4-4. 빌드타임 데이터 파이프라인

`scripts/build-game-data.ts`가 다음을 조인해 `src/data/game-data.generated.json`을 만든다.

```
  1. 공식 /brawlers               → 존재하는 브롤러 ID 목록 (기준)
  2. BrawlAPI /v1/brawlers        → 정식 영문명, 희귀도, 역할(en), 설명(en), 이미지 URL,
                                     스타파워·가젯 이름과 설명
  3. BrawlAPI /game/csv_logic/characters → 내부 코드명, Hitpoints, Speed, AutoAttackRange
  4. BrawlAPI /game/localization/kr      → 한글명, 한글 설명, 한글 역할
  5. 조인 후 정규화 벡터 계산 → 산출물 저장
```

**조인 기준은 공식 API의 브롤러 ID**다. BrawlAPI에만 있고 공식에 없는 브롤러(현재 `Buzz Lightyear`)는 제외한다.

**누락 처리 원칙 — 빌드를 실패시키지 않는다.** 신규 브롤러가 나오면 한글 데이터가 항상 늦게 들어오는데, 빌드를 막으면 브롤러가 추가될 때마다 배포가 불가능해진다.

```
  한글명 없음   → 수동 오버라이드 테이블 조회 → 없으면 영문명으로 폴백 + 경고 로그
  역할 없음     → 역할 배지를 숨김. 추천 스코어링은 수치 스탯만으로 계속 동작
  이미지 없음   → 플레이스홀더
```

현재 오버라이드가 필요한 브롤러:
```
  한글명·설명 누락 (4종)  GENE, GRAY, HANK, ANGELO
  역할 누락 (23종)        위 4종 + WENDY, NORI, BOLT, STARR NOVA, DAMIAN, NAJIA, SIRIUS,
                          GLOWY, GIGI, PIERCE, ZIGGY, MINA, TRUNK, ALLI, KAZE, JAE-YONG,

```

### 4-6. 전적 수집 전략

두 경로로 쌓는다.

**온디맨드** — 사용자가 조회할 때마다 서버가 응답을 반환하면서 `player_snapshots`에 하루 한 행 upsert하고, 배틀은 `(tag, battle_time, mode)` 유니크로 중복 제거 삽입한다. 자주 보는 계정일수록 자연히 촘촘해진다.

**주기 폴링** — 하루 1회 크론이 대표 계정으로 등록된 태그를 순회해 스냅샷을 갱신한다. 한동안 들어오지 않아도 추이 그래프에 구멍이 생기지 않는다.

폴링 대상은 무제한으로 늘어나면 안 된다.

```
  대상 조건   last_seen이 최근 14일 이내
  배치 상한   1회 300개
  순서        last_polled 오래된 순 라운드로빈
```

이 크론은 Supabase 무료 프로젝트가 7일 무활동으로 일시정지되는 것을 막는 역할도 겸한다.

## 5. 추천 알고리즘

### 5-1. 특성 벡터

역할 라벨이 아니라 **수치 스탯**을 기준으로 삼는다. 역할은 106종 중 83종만 있지만 수치는 106종 전부 있고, 신규 브롤러도 자동으로 채워진다.

```
  range       AutoAttackRange 정규화     근접 ←→ 원거리
  durability  Hitpoints 정규화           물몸 ←→ 탱커
  mobility    Speed 정규화               느림 ←→ 빠름
```

정규화는 106종 전체의 최소·최대를 기준으로 0~1로 맞춘다.

여기에 파생 축 하나를 더한다.

```
  risk = (1 − durability) × (1 − range)      물몸이면서 근접일수록 높다
```

체력이 낮고 사거리가 짧을수록 한 번의 판단 실수가 죽음으로 이어진다. 별도 데이터 없이 기존 두 축에서 계산되므로 신규 브롤러도 자동으로 채워진다.

역할 라벨이 있으면 보조 신호로 가중치를 살짝 더한다.

### 5-2. 설문 벡터 Q

**설문 문항은 브롤러 쪽에 대응 축이 있는 것만 만든다.** 대응 축이 없는 질문은 답을 받아도 점수에 반영할 방법이 없다.

```
  Q1  선호하는 교전 거리는?                → range
  Q2  앞에서 싸우나 뒤에서 지원하나?        → durability
  Q3  기동성과 화력 중 무엇을 택하나?       → mobility
  Q4  한 방을 노리다 죽는 걸 감수하나?      → risk (파생 축)
```

"조작 난이도"는 의도적으로 뺐다. 수치 스탯에서 도출할 방법이 없어서 106종을 손으로 태깅해야 하는데, 그 공수 대비 얻는 게 적다. 필요해지면 v2에서 수동 태그로 추가한다.

### 5-3. 계정 벡터 P

대표 계정이 있을 때만 계산한다.

- 보유 브롤러의 특성 벡터를 **트로피로 가중 평균**한다. 트로피를 몰아준 브롤러가 실제 선호를 드러낸다
- 랭크와 파워 레벨을 보조 가중치로 반영
- 배틀로그에서 최근 사용한 브롤러에 추가 가중치

### 5-4. 최종 점수

```
  축     range, durability, mobility, risk   (4축)
  T      α·Q + (1−α)·P      α 기본값 0.5, 대표 계정이 없으면 α = 1.0
  score  cosine(T, vector(b))
```

결과를 두 그룹으로 나눈다.

**이미 잘 쓰는 브롤러**
  - 조건: score 상위이면서 내 트로피 상위
  - 의미: 추천 결과가 말이 되는지 검증해주는 역할

**안 써봤는데 맞을 브롤러**
  - 조건: score 상위이면서 미보유이거나 트로피 하위
  - 의미: 이 기능의 실질적 가치

각 그룹 상위 5명씩 노출하고, AI가 근거 설명을 붙인다.

### 5-5. 근거 문구 조합

추천 근거는 세 조각을 이어 붙여 만든다. 실시간 AI 없이도 개인화된 문장이 나온다.

```
  [사용자 성향 문구]   규칙 기반. 벡터에서 가장 두드러진 축 1~2개를 문장으로
  [브롤러 성향 문구]   사전 생성물. 이 브롤러가 어떤 사람에게 맞는지
  [연결 문구]          규칙 기반. 두 성향이 맞는 이유 또는 보완 관계
```

사용자 성향 문구는 각 축의 값을 3구간(낮음·중간·높음)으로 나눠 미리 써둔 문장에 매핑한다. 4축 × 3구간 = 12개 문장만 번역하면 되고, 이건 UI 메시지 파일에 들어간다.

예시:
```
  range 높음 + durability 낮음
  → "당신은 원거리에서 안전하게 화력을 내는 쪽을 선호합니다."
  + "브록은 사거리가 길고 체력이 낮아 뒤에서 지속 딜을 넣는 브롤러입니다."
  + "성향이 그대로 맞아떨어집니다."
```

### 5-6. 검증 방법

추천이 말이 되는지는 자동 테스트로 확인하기 어렵다. 대신 다음을 단위 테스트로 고정한다.

- 정규화 벡터가 0~1 범위를 벗어나지 않는다
- 극단 설문 응답(전부 근접·탱커·느림)에 대해 상위 결과가 실제 고체력·단거리 브롤러다
- 파생 축 risk가 물몸 근접 브롤러에서 최대값에 가깝고 고체력 원거리 브롤러에서 최소값에 가깝다
- 대표 계정이 없을 때 α가 1.0이고 계정 벡터가 결과에 영향을 주지 않는다

## 6. 운영

### 6-1. 배포와 리전

**Vercel 함수 리전을 미국으로 둔다.** RoyaleAPI 프록시가 미국에 있어서, 함수를 한국 리전에 두면 모든 요청이 태평양을 왕복한다. 해외 타겟이라는 방향과도 맞다.

**Supabase 리전도 함수와 같은 대륙**에 둔다. 함수와 DB 사이 왕복이 사용자 체감 지연에 직접 들어간다.

정적 페이지와 에셋은 Vercel 글로벌 CDN이 처리하므로 리전 선택과 무관하다.

### 6-2. 환경변수

```
  BRAWL_STARS_TOKEN     서버 전용. 절대 NEXT_PUBLIC_ 접두사를 붙이지 않는다
  GEMINI_API_KEY        서버 전용
  DATABASE_URL          서버 전용
  CRON_SECRET           크론 엔드포인트 보호용
```

`.env.local`은 `.gitignore`에 반드시 포함한다. 브롤스타즈 토큰은 발급 후 수정이 불가능하므로, 노출되면 새 키를 만들어야 한다.

### 6-3. 정기 작업

**스냅샷 폴링** — Vercel 크론, 하루 1회. Hobby 플랜은 하루 1회보다 잦은 표현식을 쓰면 배포 자체가 실패하므로 이 주기가 상한이다.

**AI 사전 생성** — 636건을 크론이 아니라 **로컬 npm 스크립트로 수동 실행**해 만들고, 결과를 `public/data/ai/` 아래 정적 파일로 커밋한다. 게임 업데이트로 브롤러가 추가될 때만 돌리면 되는 작업이라 자동화가 필요 없다.

스크립트는 **이미 파일이 있는 브롤러를 건너뛴다.** 신규 브롤러만 생성하므로 매번 424건을 다시 만들지 않고, 사람이 손으로 고친 문장이 덮어써지지 않는다. 전체 재생성이 필요하면 `--force` 플래그로 명시한다.

### 6-4. 무료 한도 관리

```
  Vercel Hobby    함수 호출 100만/월 · CPU 4시간/월 · 대역폭 100GB/월
                  이미지 변환 5천/월 · 크론 1회/일 · 함수 60초
  Supabase Free   DB 500MB · 대역폭 5GB/월 · 7일 무활동 시 일시정지
  Gemini Free     2.5 Flash 일 1,500 요청 수준 (AI Studio에서 확인)
```

각 한도에 대한 대응:
  - 이미지 변환은 CDN 직접 사용으로 소비량 0
  - CPU 시간은 크론 배치 상한(300개)으로 통제
  - DB 용량은 원본 JSON 미저장 + 180일 보존 정책으로 통제
  - Supabase 일시정지는 하루 1회 크론이 자동으로 방지
  - Gemini 런타임 소비는 "더 물어보기"를 누른 경우로만 한정된다. 사전 생성물은 정적 파일이라 한도를 쓰지 않는다

**Gemini 프로젝트에 결제 수단을 연결하지 않는다.** 한도를 넘으면 요청이 거절될 뿐 과금이 발생하지 않는다. 이것이 "개발자에게 청구 0원"을 구조적으로 보장하는 유일한 장치다.

### 6-5. 게임 업데이트 대응

슈퍼셀 업데이트마다 신규 브롤러·모드·맵이 추가되고, 업데이트 중에는 API가 `503`을 반환한다.

- 하루 1회 크론에서 공식 `/brawlers` 개수와 번들 스냅샷 개수를 비교한다. 다르면 로그에 남긴다
- 개발자가 이를 보고 `build-game-data` 스크립트를 다시 돌려 커밋·배포한다
- 그때까지도 사이트는 정상 동작한다. 신규 브롤러는 영문명·역할 없음 상태로 노출되고, 추천 스코어링은 수치 스탯만으로 계속 돈다

### 6-6. 모니터링

공개 서비스이므로 최소한의 관측은 필요하다.

- Vercel 기본 로그로 함수 에러 추적
- 브롤스타즈 API 응답 코드별 카운트를 로그에 남겨 `403`(키·IP 문제)과 `503`(점검)을 구분한다
- AI 한도 소진 여부를 로그로 확인

### 6-7. 법적 표기

슈퍼셀 팬 콘텐츠 정책에 따라 다음을 푸터에 노출한다.

## 7. 고려해야 할 지점

### 7-1. RoyaleAPI 프록시 의존

모든 공식 API 요청이 제3자 서버를 경유한다. 그쪽에서 우리 토큰을 볼 수 있고, 그쪽이 죽으면 계정 조회 기능 전체가 멈춘다. 전적 데이터라 민감도는 낮고 커뮤니티 표준처럼 쓰이는 방식이지만, 단일 장애점인 것은 사실이다.

대안은 고정 IP를 가진 VPS에 배포하는 것이다. 트래픽이 늘거나 프록시가 불안정해지면 그때 이동한다. API 클라이언트에서 베이스 URL만 환경변수로 빼두면 전환 비용이 거의 없다.

### 7-2. BrawlAPI 비공식 의존

빌드타임에만 쓰기로 해서 런타임 리스크는 없앴다. 다만 이 API가 영영 죽으면 신규 브롤러의 한글명·이미지·설명을 얻을 경로가 사라진다. 그 경우 공식 API의 영문명과 수치 스탯만으로 축소 운영이 가능하도록 파이프라인이 폴백을 갖추고 있다.

### 7-3. 신규 유저 콜드스타트

처음 조회한 계정은 스냅샷이 한 개뿐이라 추이 그래프가 나오지 않는다. 배틀로그도 25건뿐이라 계정 벡터가 부정확하다. 이건 구조적 한계이므로 숨기지 말고 명시한다.

- 그래프 자리에 "내일부터 추이가 쌓입니다" 안내
- 추천 결과에 "데이터가 쌓일수록 정확해집니다" 표시

### 7-4. 한글 데이터가 항상 늦다

`localization/kr`은 게임 버전 스냅샷이라 최신 브롤러가 빠져 있다. 실측 시점 기준 23종의 역할, 4종의 이름이 없었다. 이건 버그가 아니라 상시 상태다. 폴백을 전제로 설계했고, 빌드를 실패시키지 않기로 한 이유가 이것이다.

### 7-5. Gemini 무료 한도의 불확실성

구글이 무료 티어 한도를 공개 문서에서 내려서, AI Studio에 로그인해야 현재 한도를 알 수 있다. 한도가 바뀌거나 정책이 변경될 수 있으므로 AI는 **없어도 서비스가 성립하는 부가 기능**으로 둔다. 추천 자체를 규칙 기반으로 만든 이유가 여기에도 있다.

### 7-6. 랭킹 200위 상한

공식 API가 제공하는 랭킹은 국가당 200위까지다. 무한 스크롤이 200에서 멈추는 건 구현 문제가 아니라 API 한계다.

여기서 파생되는 문제가 하나 있다. **대부분의 사용자는 자기 계정이 200위 안에 없으므로 "내 계정" 하이라이트를 영영 보지 못한다.** 기능이 죽어 보이지 않게, 대표 계정이 설정돼 있는데 목록에 없으면 목록 상단에 "내 순위: 200위 밖" 같은 안내를 별도로 띄운다.

### 7-7. 개인정보

게임 태그는 공개 식별자라 개인정보로 보기 어렵지만, 레이트리밋을 위해 **IP 해시를 저장**한다. 원본 IP는 저장하지 않고, `ai_usage`는 30일 후 삭제한다. 개인정보 처리방침 페이지를 두는 게 안전하다.

### 7-8. 캐시 무효화

브롤러 데이터는 빌드 산출물이라 재배포로 갱신된다. 하지만 PWA 서비스 워커가 이전 번들을 붙들고 있으면 사용자가 낡은 데이터를 본다. 서비스 워커에 버전 기반 무효화를 넣고, 새 버전 감지 시 새로고침을 안내한다.

## 8. 테스트

### 8-1. 픽스처

조사 과정에서 확보한 실제 응답을 그대로 픽스처로 쓴다. 손으로 만든 가짜 데이터보다 실제 구조를 정확히 반영한다.

```
  브롤러 106종 (공식)          /brawlers 응답
  브롤러 107종 (BrawlAPI)      /v1/brawlers 응답 — 드리프트 케이스 포함
  이벤트 로테이션 15슬롯       /events/rotation 응답 — 변형 ISO 시각 포함
  characters CSV               수치 스탯 조인 테스트용
  localization/kr              한글 매칭·누락 케이스 테스트용
```

### 8-2. 단위 테스트

- 태그 검증 — 유효 문자, `#` 처리, URL 인코딩
- 시각 파서 — `20260824T080000.000Z` 형식
- 배틀로그 파서 — 팀 모드·쇼다운·미지의 모드 세 갈래
- 빌드 파이프라인 조인 — 이름 누락 4종, 역할 누락 23종, 공식에 없는 브롤러 제외
- 특성 벡터 정규화와 추천 스코어링

### 8-3. 통합 테스트

- Route Handler — 프록시를 목킹해 `200 / 403 / 404 / 429 / 503` 각각의 처리 확인
- 랭킹 커서 페이지네이션 — 커서를 이어받아 `rank`가 끊기지 않는지, `cursors`가 비면 종료하는지, 잘못된 커서에 `400`을 반환하는지
- `/api/home` 부분 실패 — 한 조각이 실패해도 나머지 섹션이 정상 응답에 담기는지
- 이벤트 정렬 — 종료 임박순이 맞는지, 만료된 슬롯이 목록에서 빠지는지
- 대표 브롤러 계산 — 보유 브롤러 중 트로피 최고가 선택되는지, 보유 브롤러가 없을 때 폴백하는지
- `nameColor` ARGB → CSS 변환
- 레이트리밋 — 한도 도달 시 `429`와 BYOK 안내
- AI 정적 파일 — 브롤러 상세와 추천 결과 표시 시 외부 AI 호출이 발생하지 않는지
- 근거 문구 조합 — 각 축 구간에 맞는 사용자 성향 문장이 선택되는지, 사전 생성물이 없을 때 폴백하는지
- AI 생성 스크립트 — 기존 파일이 있으면 건너뛰는지, `--force`일 때만 덮어쓰는지

### 8-4. i18n 테스트

- `en`·`ko` 메시지 파일의 키 집합이 일치하는지 검사
- 게임 데이터에 두 언어 이름이 모두 있는지, 없으면 폴백이 동작하는지

E2E는 v1 범위 밖으로 둔다.

## 9. v1 범위 밖

- 로그인·소셜 인증
- **클럽 상세 — v2에 추가 예정.** 클럽 *랭킹*은 홈과 랭킹 탭에서 v1에 들어가지만, 클럽 상세와 멤버 목록(`/clubs/{tag}`, `/clubs/{tag}/members`)은 v2다. 랭킹 목록에서 클럽을 클릭했을 때 열릴 상세 패널 자리를 v1에서는 비워둔다
- **이벤트 히스토리** — 종료된 이벤트를 보여주려면 로테이션 스냅샷을 직접 쌓아야 한다. 공식 API에 과거 데이터가 없다. 필요해지면 기존 크론에 로테이션 저장을 추가하는 것으로 시작한다
- 브롤러별 랭킹(`/rankings/{country}/brawlers/{id}`) — v1은 플레이어·클럽 랭킹만
- 영어·한국어 외 로케일 — `localization/`에 23개 언어가 있어 확장은 쉽다
- 네이티브 앱 빌드 — PWA manifest까지만
- AI 자유 대화
- 맵·게임모드 상세 도감
