## 이 플랜은 설계서 2-8 을 바꾼다

설계서는 AI 를 이렇게 잡아뒀다.

```
  사전 생성   브롤러 사용법·기어·성향 636건을 정적 파일로            미구현 (키 필요)
  실시간      추천 결과의 [AI에게 더 물어보기] 버튼만                v1.5
  자유 입력   v1 에서 제외 — 프롬프트 인젝션과 한도 폭주를 막기 위해
```

**자유 입력을 v1 에 넣기로 했다.** 대신 BYOK 로 가서 원래 걱정하던 두 가지가 성격이 달라진다.

```
  한도 폭주        사용자 자기 키라 개발자 과금이 0. 한도도 사용자 것
  프롬프트 인젝션   사용자가 자기 키로 자기에게 하는 질문. 남의 데이터가 섞이지 않는다
  없는 브롤러 지어냄  ← 이건 그대로 남는다. 그라운딩으로 막는다
```

세 번째만 실제 위험으로 남는다.

## 실측으로 확인한 것 — 브라우저에서 직접 부를 수 있다

BYOK 의 핵심은 **키가 우리 서버를 지나가지 않는 것**이다. 그러려면 브라우저가 AI API 를 직접 불러야 하는데, CORS 가 막으면 불가능하다. 세 곳을 실제로 재봤다.

```
  Gemini      generativelanguage.googleapis.com   CORS OK    400 (잘못된 키)
  OpenAI      api.openai.com/v1                    CORS OK    401
  Anthropic   api.anthropic.com/v1                 차단       TypeError: Failed to fetch
              └ anthropic-dangerous-direct-browser-access: true 헤더를 넣으면  CORS OK  401
```

세 곳 다 브라우저 직접 호출이 된다. 에러도 읽을 수 있는 JSON 이라 사용자에게 원인을 그대로 보여줄 수 있다.

**그래서 서버 라우트를 만들지 않는다.** 키가 우리 서버로 오지 않으니 유출 경로 자체가 없다. 설계서 2-8 의 "호출은 서버 라우트에서만 한다"는 공용 키를 전제한 규칙이라 BYOK 에는 반대로 적용된다.

## 모델 이름을 코드에 박지 않는다

모델명은 자주 바뀌고, 내가 아는 이름이 이미 낡았을 수 있다. **키를 넣으면 그 API 에서 모델 목록을 받아 드롭다운을 채운다.**

```
  Gemini      GET /v1beta/models?key=…
  OpenAI      GET /v1/models          Authorization: Bearer …
  Anthropic   GET /v1/models          x-api-key + 위 헤더
```

목록을 못 받으면 사용자가 직접 입력할 수 있게 둔다. 추측한 기본값으로 조용히 실패하지 않는다.

## 설계 결정

### 진입점은 탭이 아니라 떠 있는 버튼이다

`tabs.ts` 에 이미 이렇게 적혀 있다 — "모바일 하단 탭바가 5개 상한". 6번째 탭을 넣을 수 없다.

떠 있는 버튼이 오히려 맞다. **어느 페이지에서든 열리고, 보고 있던 것을 질문에 실어 보낼 수 있다.** 브롤러 상세를 보다가 "얘 어떻게 써?" 를 그 자리에서 물을 수 있다.

패널은 `DetailPanel` 을 그대로 쓴다 — 데스크톱 오른쪽 드로어, 모바일 바텀시트가 이미 되어 있다.

**`AppShell` 이 아니라 `layout.tsx` 에 마운트한다.** AppShell 은 다른 작업(아이콘·로고)이 지금 건드리고 있어 충돌을 만들 이유가 없다. 전역 오버레이라 레이아웃에 두는 게 구조적으로도 맞다.

### 없는 브롤러를 지어내지 않게 그라운딩한다

이게 유일하게 남은 실제 위험이다.

```
  시스템 프롬프트에 넣는 것
    - 브롤러 106종의 이름 목록 (현지화된 이름 포함)
    - 지금 보고 있는 브롤러가 있으면 그 브롤러의 스탯·능력 설명
    - 설문 벡터가 있으면 사용자 성향
    - "목록에 없는 브롤러를 언급하지 말 것"
```

106종 전체 스탯을 매번 넣으면 토큰이 아깝다. **이름 목록만 항상 넣고, 상세는 화제에 오른 브롤러만 넣는다.**

### 주제는 좁히되 막지는 않는다

브롤러·추천·게임 관련 위주로 답하도록 시스템 프롬프트에서 안내한다. 벗어난 질문을 **거부하지는 않는다** — 자기 키로 자기 질문을 하는데 우리가 막을 이유가 없다.

### 스트리밍은 하지 않는다

v1 은 요청 하나에 응답 하나다. 스트리밍은 세 provider 의 형식이 전부 달라 어댑터가 세 배가 된다. 답이 짧아 체감 차이도 작다.

### 키는 로컬스토리지에 둔다

```
  byok: { provider: 'gemini' | 'openai' | 'anthropic', model: string, key: string } | null
```

기존 `byokKey: string | null` 을 대체한다. 읽는 곳이 아직 없어 안전하게 바꿀 수 있다.

**정직하게 적어둘 한계** — 로컬스토리지의 키는 같은 오리진의 스크립트가 읽을 수 있다. 우리 앱은 사용자 입력을 HTML 로 렌더하지 않지만, XSS 가 생기면 키가 샌다. 키 입력 화면에 이 사실과 "권한이 최소인 키를 쓰라"는 안내를 함께 둔다.

### 대화는 저장하지 않는다

패널을 닫으면 사라진다. 로컬스토리지에 쌓으면 용량 관리와 삭제 UI 가 따라오는데, v1 에서 그만한 가치가 없다.

# Tasks

### Task 1: 어댑터 (`src/lib/ai/providers.ts`)

세 provider 의 차이는 네 가지뿐이다. 그것만 어댑터로 감싼다.

```ts
export interface Adapter {
  /** 모델 목록 요청. 실패하면 사용자가 직접 입력한다 */
  listModels(key: string): { url: string; init: RequestInit }
  parseModels(json: unknown): string[]
  chat(key: string, model: string, system: string, messages: ChatMessage[]):
    { url: string; init: RequestInit }
  parseChat(json: unknown): string
  /** API 가 준 에러 메시지를 그대로 꺼낸다. 우리가 지어내지 않는다 */
  parseError(status: number, json: unknown): string
}
```

**Anthropic 은 `anthropic-dangerous-direct-browser-access: true` 가 없으면 CORS 로 막힌다.** 실측으로 확인했다.

테스트는 네트워크 없이 한다 — 요청 URL·헤더·바디 조립과, 실제 응답 형태를 넣었을 때의 파싱만 본다.

### Task 2: 그라운딩 프롬프트 (`src/lib/ai/prompt.ts`)

```ts
export function buildSystemPrompt(opts: {
  locale: Locale
  brawlerNames: string[]
  focus?: Brawler | null      // 지금 보고 있는 브롤러
  survey?: Vector | null      // 설문 성향
}): string
```

- 106종 이름을 목록으로 넣고 "이 목록에 없는 브롤러는 언급하지 말 것"
- `focus` 가 있으면 그 브롤러의 스탯·스타파워·가젯 설명을 붙인다
- `survey` 가 있으면 축별 성향을 문장으로
- 답변 언어를 `locale` 로 고정

테스트: 이름 목록이 전부 들어가는지, focus 가 없으면 상세가 안 붙는지, 언어 지시가 locale 을 따르는지.

### Task 3: `useByok`

`storage.Settings.byok` 를 읽고 쓴다. `useMainAccount` 와 같은 패턴(이벤트 동기화)을 따른다.

### Task 4: `KeySetup`

provider 선택 → 키 입력 → **모델 목록을 그 API 에서 받아** 드롭다운. 목록 실패 시 직접 입력.

키 입력란은 `type="password"`. 저장 위치와 위험을 화면에 그대로 적는다.

### Task 5: `ChatPanel`

- 키가 없으면 `KeySetup`
- 있으면 대화. 전송 → 어댑터로 직접 호출 → 응답 추가
- 실패하면 **API 가 준 메시지를 그대로** 보여준다 (401 이면 키 문제라고 안내)
- 대화 중 provider/키 변경 진입점

### Task 6: `ChatLauncher` 를 레이아웃에 마운트

떠 있는 버튼. 모바일에서는 하단 탭바 위로 띄운다. `layout.tsx` 의 `AppShell` 바깥에 둔다.

## 완료 조건

```
  □ 키 없이 열면 안내와 입력 화면이 뜬다 (규칙 기반 기능은 그대로 동작)
  □ 잘못된 키를 넣으면 API 가 준 에러 메시지가 그대로 보인다
  □ 유효한 키로 모델 목록이 채워진다
  □ 질문에 답이 오고, 없는 브롤러를 지어내지 않는다
  □ 브롤러 상세를 보다 열면 그 브롤러가 질문 맥락에 들어간다
  □ 키가 우리 서버로 가지 않는다 (네트워크 탭에 우리 도메인 호출이 없다)
  □ npx tsc --noEmit && npx eslint . && npm test 통과
```

## 리뷰에서 걷어낸 것

처음 구현에 필요 없는 층이 있었다.

```
  Adapter.parseError    세 provider 가 전부 같은 함수를 가리키고 있었다 → describeError 하나로
  isProvider            아무도 쓰지 않았다 → 삭제
  ADAPTERS export       adapterFor 가 있으면 충분하다 → 내부로
  run(call, parse, a)   parse 는 항상 a.parseChat 이었다 → 인자 삭제
```

**ChatPanel 이 `h-full` 로 자체 스크롤을 만들고 있었다.** `DetailPanel` 이 이미 스크롤 컨테이너라 중첩되면 모바일 바텀시트에서 입력창이 화면 밖으로 밀린다. 바깥 스크롤을 그대로 쓰고 입력창만 `sticky` 로 붙였다.

**응답이 오기 전에 패널을 닫으면 언마운트된 컴포넌트의 상태를 건드렸다.** `alive` ref 로 막았다.

**히스토리를 무제한으로 실어 보내고 있었다.** 매 요청이 전체 대화를 다시 보내므로 토큰이 계속 커지는데 요금은 사용자 몫이다. 최근 12턴으로 잘랐다.
