## 실측으로 확인한 것 — 설계서 5-3 을 고쳐야 한다

**설계서는 "보유 브롤러의 특성 벡터를 트로피로 가중 평균" 하라고 되어 있는데, 그렇게 하면 신호가 나오지 않는다.** 실제 계정 두 개로 재봤다.

```
                       전체 평균 벡터와의 편차 (4축 절대차 합)
  전체 트로피 가중        0.001 ~ 0.009      ← 사실상 전체 평균과 같다
  평균 초과분 가중        0.088 ~ 0.102
  상위 20종 평균         0.083 ~ 0.099
  상위 10종 평균         0.126 ~ 0.221      ← 가장 크고 두 계정 모두 안정적
```

이유는 단순하다. 상위권 계정은 **106종을 전부 보유**하고 트로피도 몰려 있다 (VITAL SHARK 2705~3048, 표준편차 29). 전부를 평균 내면 전체 평균이 그대로 나온다.

```
  P = 트로피 상위 10종의 단순 평균
```

보유가 10종 미만이면 있는 만큼만 쓴다. 트로피 가중은 하지 않는다 — 상위 10종 안에서는 트로피 차이가 선호를 더 설명하지 못한다.

**미보유로 "안 써본 브롤러"를 가릴 수 없다.** 두 계정 다 106/106 보유였다. 그룹 분리 기준은 보유 여부가 아니라 **그 계정 안에서의 트로피 순위**로 잡는다.

## 실측으로 확인한 것 — 숫자만으로는 변별이 안 된다

설문 3종으로 상위 5명과 점수 스프레드를 재봤다.

```
  원거리·안전 선호   브록 89 · 러프스 89 · 맨디 89 · 이브 89 · 콜트 89     스프레드 0.2p
  근접·탱커 선호     엘 프리모 82 · 드라코 80 · 애쉬 80 · 샘 79 · 데미안 78  스프레드 4.1p
  기동·한방 선호     키트 89 · 미코 85 · 셰이드 83 · 노리 82 · 에드거 81    스프레드 7.9p
```

**순위 자체는 타당하다** — 원거리에 저격수, 근접에 탱커, 기동에 어쌔신이 나온다. 문제는 원거리처럼 극단적인 답을 고르면 5명이 전부 89%로 붙는다는 것이다. 설계서가 예상한 3.6~8.5p 보다 훨씬 좁은 경우가 실재한다.

**그래서 퍼센트는 보조로만 쓰고, 축 일치 배지를 주 정보로 둔다.** "89%" 다섯 개는 정보가 아니지만 "사거리 일치 · 생존력 일치"는 정보다.

## 설계 결정

### AI 사전 생성물 없이 완결시킨다

설계서 5-5 는 근거 문구를 [사용자 성향] + [브롤러 성향(사전 생성)] + [연결] 세 조각으로 만든다. **브롤러 성향 636건은 아직 생성되지 않았다** (Gemini 키 필요, STATUS 의 남은 작업).

없는 것을 전제로 만들지 않는다. v1 은 규칙 기반 두 조각으로 문장을 만들고, 사전 생성물이 생기면 가운데에 끼워 넣을 자리만 비워 둔다.

```
  [사용자 성향]  4축 × 3구간 = 12문장. 메시지 파일에 들어간다
  [축 일치]      가장 잘 맞는 축 1~2개를 배지와 문장으로
  (브롤러 성향)  자리만 비워 둔다. 사전 생성물이 생기면 채운다
```

### 설문은 클라이언트 전용이고 페이지는 정적이다

설문 답은 로컬스토리지에 있고 서버는 모른다. 계정 벡터도 대표 계정이 있어야 나온다. **페이지는 정적 셸만 그리고 결과는 전부 클라이언트에서 계산한다.**

브롤러 106종 벡터는 이미 번들에 있으므로 계산에 네트워크가 필요 없다. 대표 계정이 있을 때만 `/api/player/[tag]` 를 부른다 — 홈·랭킹과 같은 쿼리 키라 요청이 합쳐진다.

`useSearchParams` 를 쓸 일이 없다. 설문 상태를 URL 에 두지 않는다.

### 결과 그룹은 계정이 있을 때만 나눈다

```
  대표 계정 없음   상위 10명을 한 목록으로
  대표 계정 있음   내 트로피 상위 절반 → "이미 잘 쓰는"
                  내 트로피 하위 절반 → "안 써봤는데 맞을"
                  각 5명
```

계정이 없으면 나눌 기준이 없다. 억지로 나누지 않는다.

### α 는 0.5 고정이다

설계서대로 `T = α·Q + (1−α)·P`, 대표 계정이 없으면 `α = 1.0`. 계정이 있으면 0.5. 사용자가 조절하는 슬라이더는 만들지 않는다 — 조절해도 뭐가 달라지는지 설명할 방법이 없다.

# Tasks

### Task 1: 순수 함수 (`src/lib/recommend.ts`)

```ts
export type Axis = 'range' | 'durability' | 'mobility' | 'risk'
export interface Vector { range: number; durability: number; mobility: number; risk: number }

/** 설문 선택지 → 축 값. 문항마다 3~4지선다 */
export const QUESTIONS: { axis: Axis; options: { key: string; value: number }[] }[]

/** 트로피 상위 N종의 단순 평균. 전체 가중 평균은 전체 평균과 같아져 신호가 없다 */
export function accountVector(brawlers: PlayerBrawler[], topN?: number): Vector | null

/** T = α·Q + (1−α)·P. 계정이 없으면 α = 1 */
export function blend(q: Vector, p: Vector | null, alpha?: number): Vector

/** 1 − ‖T−v‖/2. 4축이 0~1이라 최대 거리는 2 */
export function score(t: Vector, v: Vector): number

/** 가장 잘 맞는 축. 차이가 작은 순으로 최대 2개, 임계값을 넘으면 버린다 */
export function matchingAxes(t: Vector, v: Vector, max?: number): Axis[]

/** 각 축을 낮음·중간·높음 3구간으로 */
export function axisBand(v: number): 'low' | 'mid' | 'high'

export function recommend(t: Vector, brawlers: Brawler[], owned?: Map<number, number>): {
  familiar: Scored[]
  fresh: Scored[]
}
```

테스트:
- `accountVector` 가 106종 균등 보유에서도 상위 10종만 본다 (전체 평균과 다르다)
- 보유 10종 미만이면 있는 만큼만
- 보유 0이면 null
- `score` 가 동일 벡터에서 1, 최대 거리에서 0
- `blend` 가 p 없으면 q 를 그대로
- `matchingAxes` 가 차이가 큰 축을 버린다
- 그룹 분리가 트로피 순위 기준으로 동작한다

### Task 2: 메시지 추가

```
  title · retake · noAccount · groupFamiliar · groupFresh · matchScore

  axis.range/durability/mobility/risk 축 이름

```

### Task 3: `SurveyForm`

4문항을 한 화면에 세로로 놓는다. 단계별 전환은 만들지 않는다 — 4개뿐이라 한눈에 보는 게 낫고, 다시 할 때 어디를 바꿀지 바로 보인다.

답하면 즉시 `saveSettings` 로 저장한다. 4개를 다 고르면 결과로 넘어간다.

### Task 4: `ResultList`

- 카드마다: 브롤러 초상 · 이름 · 매칭 퍼센트 · 축 일치 배지 · 근거 한 줄
- 배지는 축 이름 그대로 ("사거리 일치")
- 근거는 [브롤러 특성 구절] + [연결 문구]

**구현하며 바꿨다.** 처음에는 [사용자 성향 문장] + [연결] 이었는데, 사용자 성향은 브롤러가 바뀌어도 같아서 다섯 카드에 똑같은 문장이 반복됐다. 사용자 성향은 목록 위에 한 번만 쓰고, 카드에는 그 브롤러의 특성을 쓴다.

브롤러 특성은 벡터에서 뽑는다 — 사전 생성물 없이도 "긴 사거리 · 낮은 체력" 은 나온다. **단 `risk` 는 설명에서 뺀다.** `risk = (1−durability)(1−range)` 라 파생값이고, 함께 쓰면 "긴 사거리 · 안정적인 운영" 처럼 같은 말을 두 번 하게 된다. 점수 계산에는 그대로 쓴다.

### Task 5: `RecommendView`

- 설문 답이 없으면 `SurveyForm`, 있으면 결과
- 대표 계정이 있으면 `/api/player/[tag]` 로 계정 벡터를 만든다. 실패해도 설문만으로 결과를 낸다
- [다시 하기] 로 설문으로 되돌아간다

### Task 6: 페이지 연결

정적 셸만 그린다. `revalidate` 도 데이터 조회도 필요 없다.

## 구현하며 잡은 함정

**축 값이 0.95 와 0.05 로 대칭이면 부동소수점 때문에 순서가 뒤집힌다.** `|0.95−0.5|` 는 `0.44999…`, `|0.05−0.5|` 는 `0.45000…` 이라 그냥 비교하면 뒤쪽이 이긴다. `dominantAxis` 가 "원거리 선호"를 "안전 선호"로 잘못 골랐고, `standoutAxes` 도 같은 문제가 있었다 (테스트가 잡았다). 두 곳 모두 엡실론을 두고 축 순서로 가른다.
